## 四、P0-A 卡种课程权限

### 1. 建表

`src/db/schema.ts` 新增：

```ts
export const cardTypeCourses = pgTable("card_type_courses", {
  id: serial("id").primaryKey(),
  cardTypeId: integer("card_type_id").notNull(),
  courseCategoryId: integer("course_category_id").notNull(),
  createdAt: timestamp("created_at", { mode: "string" }).notNull().defaultNow(),
}, (t) => ({ uniq: uniqueIndex("card_type_courses_uniq").on(t.cardTypeId, t.courseCategoryId) }));
```

迁移方式：项目只有 `drizzle/0000_complex_klaw.sql` 一个初始迁移。用 `npx drizzle-kit generate` 生成 SQL 后，写一个一次性 node 脚本用 `rawSql` 执行（不要用 drizzle-kit push 直连生产库自动改）。脚本必须：先备份 card_types 到 `backups/`，再执行 DDL，并打印结果。执行前把 SQL 给用户看一遍。

### 2. 后台卡类型接口

`src/app/api/admin/card-types/route.ts`：

- GET 返回每个卡种时，附带 `courseCategoryIds: number[]`
- POST 与 PUT 接受 `courseCategoryIds`，写卡种后同步写 `card_type_courses`（先删后插，事务内）

### 3. 后台 UI

`src/app/admin/cards/page.tsx` 里「卡类型配置」抽屉（约 705 行起）：

- 现有卡种列表每项显示已勾选的课程名
- 新增卡类型表单与编辑表单加「适用课程」多选框（5 个课种）
- 文案固定：「勾选该卡可以预约的课程，一卡通类卡勾全部」

### 4. 会员端预约校验

`src/app/api/portal/bookings/route.ts`，现有校验在约 65 到 90 行（只查有没有有效卡）。改成：

```sql
SELECT mc.id, ct.category
FROM member_cards mc
JOIN card_types ct ON ct.id = mc.card_type_id
JOIN class_sessions s ON s.id = ${sessionId}
WHERE mc.tenant_id = 1 AND mc.member_id = ${memberId}
  AND mc.status = 'active'
  AND (mc.valid_from IS NULL OR mc.valid_from::date <= CURRENT_DATE)
  AND (mc.valid_until IS NULL OR mc.valid_until::date >= CURRENT_DATE)
  AND (ct.category = 'period' OR mc.remaining_count > 0)
  AND EXISTS (
    SELECT 1 FROM card_type_courses ctc
    WHERE ctc.card_type_id = ct.id
      AND ctc.course_category_id = s.course_category_id
  )
ORDER BY CASE WHEN ct.category = 'period' THEN 0 ELSE 1 END,
         CASE WHEN mc.valid_until IS NULL THEN 1 ELSE 0 END,
         mc.valid_until, mc.id
LIMIT 1;
```

错误提示分三种，不要混：

- 完全没有有效卡：`还没有有效会员卡，请联系小桥开卡后再预约`（422）
- 有卡但卡种不允许这节课：`这张卡不能约${课程名}，请使用${允许的卡名}或联系小桥`（422）
- 卡过期、冻结、次数不足：`会员卡已冻结、过期或次数不足，暂不能预约`（422）

**过渡策略**：某卡种在 `card_type_courses` 里没有记录时，视为「未配置」，暂不拦截（避免上线即锁死会员）；后台一旦勾选就立即拦截。请在返回里带一个标记，便于排查。

### 5. 教练端扣次

`src/app/api/coach/check-in/route.ts`，两处查候选卡的 SQL（约 35 到 45 行、87 到 92 行）：

- 候选卡必须覆盖这节课的课种（JOIN bookings → class_sessions → course_category_id，再 EXISTS card_type_courses）
- 排序改为：先扣覆盖面更窄的专用卡（`card_type_courses` 条数少的优先），再扣通卡；同类型按最早到期
- 如果这节课没有任何覆盖卡，返回 422 并提示「该会员没有可扣这节课的卡」，不要扣任何卡、不要写考勤

### 6. 会员端展示

`miniprogram/pages/cards/cards.js` 与 `.wxml`：每张卡显示「可约：瑜伽 / 普拉提 / 大器械 / 维密 / 私教」，来自 `/api/portal/cards` 返回的 `courseCategoryNames`。

`miniprogram/pages/booking/booking.js` 与 `.wxml`：预约失败时展示服务端返回的中文提示（现在可能是通用文案），确保会员看得懂是哪张卡不对。

## 五、P0-B 批量导入给已有会员补卡（当前是 bug）

`src/app/api/admin/members-import/route.ts` 第 102 到 104 行：

```ts
if (phone && phoneOwner.has(phone)) {
  results.push({ line, status: "skipped", name, reason: "手机号已存在（会员 id " + phoneOwner.get(phone) + "），未重复创建" });
  continue;              // ← 这一跳，卡也没开
}
```

要求改成：

1. 手机号命中已有会员 → 取该会员 id，`isExistingMember = true`，跳到开卡逻辑；没有值可开卡时返回 `skipped` 并写原因
2. 手机号没命中时，再按「会员编号 → 唯一姓名」匹配；重名或无法唯一匹配且没有手机号的行，状态标记为 failed，原因写「重名，请补手机号或会员编号」，不要猜
3. 开卡逻辑保持幂等（现有 idempotency_key 机制），重复导入不会重复开卡
4. 返回结果里对老会员补卡标注 `matchedBy: "phone" | "memberCode" | "name"`，结果表与导出 CSV 带上这一列

测试用例必须覆盖：

- 新会员 + 开卡
- 老会员（手机号命中）+ 补卡
- 老会员（无手机号，姓名唯一）+ 补卡
- 重名 + 无手机号 → failed，不写库
- 同一行重复导入两次 → 第二次 skipped
- 卡名不存在 → 会员照建，卡不建，原因写清楚
