## 0. 一句话结论

1. **退卡不需要新建表**，`member_cards` 加 `returned` 状态 + 3 个列即可；剩余次数**保留不扣**，靠状态拦截使用。
2. 现有预约/签到两处 SQL 已经写死 `mc.status = 'active'`，所以 `returned` 一旦落库，**权益自动失效**；但**错误文案会误报成"冻结/过期/次数不足"**，必须改文案并抽成公共判定。
3. 权限是本方案最大的技术债：后台现在**只验"有没有登录"，不验"是什么角色"**，且存在两套并存的会话体系（详见 2.3-B）。不修这个，退卡"只有店主能做"就只是文档上的一句话。

## 一、已确认规则（本版锁定，不再讨论）

### 1.1 退卡

| # | 老板原话要点 | 系统含义（实现口径） |
|---|---|---|
| 1 | 退卡由 `owner` 统一决定和处理，其他角色无权办理、无权决定剩余权益处理方式 | 退卡接口硬编码 `requireRole("owner")`；manager/frontdesk/coach 一律 403；接口不提供"剩余权益处理方式"参数 |
| 2 | 退卡时剩余次数及关联权益全部冻结，不得继续预约、签到核销、使用该卡权益 | `member_cards.status = 'returned'`；预约/签到/核销统一判定为不可用 |
| 3 | 冻结不等于清零或删除，必须保留退卡前剩余次数、卡项信息、原始流水、完整操作记录 | `remaining_count` **原值保留不写 0**；`card_types`、`card_transactions` 不动；`audit_logs` 写 before/after |
| 4 | 剩余权益如何处理由店主向会员说明并决定，系统不得自行推断或自动执行退款、清零、返现 | 退卡接口只置状态、只写流水（金额 0）、只写审计；**无任何金额变动、无任何自动清零** |
| 5 | 必须记录操作人、时间、原因、前后卡状态及剩余权益；未授权不得恢复或修改退卡后权益 | `audit_logs`(actor_type/actor_id/actor_role/action/entity/before_json/after_json/reason) + `member_cards.returned_at/return_reason` |
| 6 | 区分"冻结"和"已退卡"，避免后续误恢复 | 新增 `returned`，与 `frozen` 并列且优先级最高；退卡后冻结/解冻接口必须拒绝 |

### 1.2 支付功能边界

| # | 规则 | 落实 |
|---|---|---|
| 1 | 小程序与后台均**不开发**在线支付、微信支付、自动退款、充值支付 | 不开支付模块、不接支付 SDK、不做支付回调 |
| 2 | 开卡/续卡/退卡/人工调整按线下业务处理，保留操作与交易记录 | 继续用 `card_transactions` 记账，`created_by` + `note` 记录线下事实 |
| 3 | **不得为了记录线下业务而虚构实际收款、退款或支付成功状态** | 禁止写 `paid` / `refunded` / `payment_status` 之类字段或状态；`price_cents` 只作为"卡面价"参考，不代表已收款；退卡流水 `amount = 0`、`type = 'return_freeze'`，**不写退款金额** |

> 落地检查：全仓库现有代码没有支付网关调用；`member_cards.price_cents` 是卡面价，不构成支付记录。本次不新增任何收付款语义。

### 1.3 退卡后会员账户与数据保留

| # | 规则 | 落实 |
|---|---|---|
| 1 | 原则上保留全部历史数据 **3 个月** | 退卡时写入 `returned_at`，到期日 = `returned_at + 3 个月`，**仅记录 + 提醒** |
| 2 | 退卡不等于删除账户或历史数据；不得因退卡自动清空训练档案、删除对比图、覆盖历史 | 退卡接口不 DELETE、不 UPDATE 任何历史表 |
| 3 | 会员仍可登录，可查看允许保留的历史资料 | 登录链路完全不变（`/api/portal/login` 不看卡状态） |
| 4 | 不可约课、签到核销、使用次数、享受会员权益 | 后端接口统一校验，不靠前端隐藏按钮 |
| 5 | 退卡状态必须与普通冻结区分，避免误恢复 | 见第三章状态机 |
| 6 | 退卡后不得自动恢复权益；恢复必须由有权限人员明确操作并留痕 | **已确认：不提供"恢复原卡"。** 需要继续消费时，由店主按**新开卡流程**重新办理（见 1.4-2、5.4） |
| 7 | 退卡后数据进入只读；不得自动新增训练记录、更新进度、生成新对比 | 会员端所有写接口 + 教练端写课后记录，全部加 `returned` 拦截 |
| 8 | 确需更正历史资料须授权人员主动操作并留痕 | 沿用 S7-B 的人工调整 + 审计模型 |
| 9 | 系统技术日志与业务数据区分，不得把日志当训练数据 | 审计只进 `audit_logs`，不写 `trainings` / `attendance` |
| 10 | 到期后如何处理需店主另行确认；未授权不得自动删除 | 到期只产生"待处理"提醒，无删除逻辑 |
| 11 | 审计记录、交易流水属可追溯记录，与普通会员资料**分开管理**，不随 3 个月一起删 | 数据保留矩阵单列（见 7.3） |

### 1.4 退卡后续处理（2026-10-22 补充确认）

| # | 已确认规则 | 系统含义 |
|---|---|---|
| 1 | 退卡后**不允许继续核销或使用**任何会员权益 | 预约、签到核销、扣次、写训练记录全部后端拦截；已有 `booked` 预约**保留历史记录，不自动取消** |
| 2 | 未来预约**由店主处理**（取消或特殊安排） | 系统不自动取消、不自动退款、不自动转课；店主可人工取消（释放名额、不扣次）或在店内核销时按个案处理 |
| 3 | **退卡不提供直接恢复** | 无 `restore` 接口；`returned` 为终态。需要继续消费 → 按**新开卡流程**重新办一张新卡，旧卡与旧流水保持只读 |
| 4 | **期限卡**退卡：保留原始有效期、退卡时间、历史权益信息，**不虚构剩余次数** | 期限卡 `remaining_count` 保持 `NULL`，不得为显示好看而写 0 或写任何数字；会员端只展示"有效期至 X，已退卡" |
| 5 | **所有退课必须由店主审批并执行** | `退课` 归入 S7-D，权限固定为 owner；退课定义（取消预约？退回次数？）仍待定，但**审批人已锁定为店主** |

### 2.3 本版新发现的三个结构性问题（必须一起改）

**A. 卡可用性判断在两处内联复制，文案已不够用**

| 位置 | 内容 |
|---|---|
| `api/portal/bookings/route.ts:64-82` | 一段 SELECT 判可用 + `anyCard` 再查一次出文案 |
| `api/coach/check-in/route.ts:34-46`（CTE 内）与 `:86-94`（失败后诊断） | 同一套规则再写一遍 |

影响：退卡进来后，改一处漏一处；且现有文案 `"会员卡已冻结、过期或次数不足"` 对退卡会员是错的，会员会以为自己的卡只是"冻结"。
→ 抽 `src/lib/cards/entitlement.ts`，两个接口 + 未来所有调整接口共用同一个判定与文案。

**B. 权限两套体系并存，角色实际不生效**

| 体系 | 位置 | 校验依据 | 谁在用 |
|---|---|---|---|
| `requireAdmin` | `lib/auth/admin-session.ts:143` | **只读 legacy cookie**（`admin_session` + 签名），JSON 里带 role，**不查库** | 所有 `/api/admin/**` |
| `requireRole` | `lib/auth/rbac.ts:62` | `admin_token` cookie → 查 `admin_sessions` 表 → 取 `users.role` | 目前**没有任何路由在用** |

后果：
1. 现在任何后台账号（含 coach/viewer）都能开卡、冻结、续卡 —— 规则"只有 owner 能退卡"必须靠新体系才能实现。
2. 两套 cookie 任一缺失行为不同：`admin_token` 写入 `admin_sessions` 失败时代码只 `console.warn` 继续登录（`admin-session.ts:98-118`），此时 `requireRole` 会判定失败，而 `requireAdmin` 仍放行。
3. legacy cookie 里的 role 是登录时快照，7 天内改角色不生效。

→ S7 统一到 `requireRole`，退卡用 `owner`；同时决定 legacy cookie 是保留（作为会话降级）还是下线。**这是退卡能否合规的前置条件。**

**C. `members.freeze_status` 与卡状态是两件事，不能混用**

`members.freeze_status / freeze_start / freeze_end` 是**会员账户级暂停**（会员列表、后台可见）；`member_cards.status` 是**单卡状态**。退卡只动卡，不动会员账户 —— 规则 1.3 明确"会员仍可登录、查看历史"，若误把 `freeze_status` 设成 frozen，会让后台把退卡会员当"暂停会员"处理，容易误恢复。

## 三、状态机

### 3.1 `member_cards.status` 目标取值

| 值 | 含义 | 权益可用 | 可逆 | 谁产生 |
|---|---|---|---|---|
| `active` | 正常 | 是（在有效期且有余次） | — | 开卡/续卡/解冻 |
| `frozen` | 普通冻结 | 否 | 是（解冻→active） | manager/owner |
| `exhausted` | 次数用尽 | 否 | 是（加次→active） | 签到扣到 0 |
| `expired` | 已过有效期 | 否 | 是（续卡→active） | 时间到达 |
| **`returned`** | **已退卡** | **否** | **否**（终态；继续消费走新开卡） | **仅 owner** |

### 3.2 转移表

| 起点 | 事件 | 终点 | 剩余次数 | 流水 | 审计 |
|---|---|---|---|---|---|
| active / frozen / exhausted / expired | 退卡（owner） | **returned** | **原值保留** | `return_freeze`, amount 0, balance_after=原余额 | 写 |
| frozen | 解冻 | active | 不变 | `adjust`, 0 | 写 |
| active | 冻结 | frozen | 不变 | `adjust`, 0 | 写 |
| active | 签到到课/未到 | active 或 exhausted | -1（次数卡） | `deduct`, -1 | 写（S7-A 补） |
| **returned** | 冻结 / 解冻 | **拒绝 409** | — | — | — |
| **returned** | 退卡（重复） | 幂等返回原结果 200 | 不变 | 不重复写 | 不重复写 |
| **returned** | 恢复原卡 | **拒绝（无接口）** | — | — | — |
| **returned** | 继续消费 | **另开一张新卡**（新卡 active，旧卡仍 returned） | 旧卡不动 | 新卡 `purchase` | 写 |
| **returned** | 未来 `booked` 预约 | **保留历史，不自动取消**；由店主人工处理 | — | — | 店主取消时写 |

> 退卡后冻结接口返回 409 而不是 200：防止 UI 上把 `returned` 覆盖成 `frozen` 而"看起来可恢复"。
> "新开一张卡"必须新建 `member_cards` 行，**不得**把旧行改回 `active`，否则历史卡项与流水会被嫁接到新业务上。

### 3.3 与会员级状态的区别

| 维度 | `member_cards.status` | `members.freeze_status` |
|---|---|---|
| 作用域 | 单张卡 | 整个会员账户 |
| 谁影响 | 开卡/续卡/冻结/退卡/签到 | 会员暂停营业期 |
| 退卡是否改 | **改**（→ returned） | **不改** |
| 是否影响登录 | 不影响 | 不影响 |
| 是否影响看历史 | 不影响 | 不影响 |

### 3.4 会员端展示优先级（`api/portal/cards/route.ts:7-12` 要改）

现状：`frozen → expired → exhausted → active`
目标：**`returned → frozen → expired → exhausted → active`**（退卡最优先，否则一张"已退卡但已过期"的卡会显示成"已过期"，会员以为还能续）

新增返回字段：`status: "returned"`、`returnedAt`、`returnReason`、`retentionUntil`（3 个月到期日）、`remainingCount`（保留原值，前端展示"剩余 N 次（已冻结）"）。

### 3.5 「权益是否可用」的唯一判定

```
可用 ⇔ status = 'active'
      AND (valid_from IS NULL OR valid_from <= today)
      AND (valid_until IS NULL OR valid_until >= today)
      AND (category = 'period' OR remaining_count > 0)
```

`returned` 天然被第一条排除。**新增约束：所有"不可用"分支必须能区分原因**，文案分级：

| 情形 | 文案（会员端） | 文案（教练端） |
|---|---|---|
| 无任何卡 | 请先办理会员卡后再预约 | 该会员暂无会员卡 |
| 全部已退卡 | 会员卡已办理退卡，如有疑问请联系小桥 | 该会员会员卡已退卡，无法核销 |
| 有退回无可用 | 会员卡已冻结、过期或次数不足，暂不能预约 | 会员卡冻结/过期/次数不足 |

### 4.2 实现要求

1. `/api/admin/member-cards/*` 全部从 `requireAdmin` **改为 `requireRole("manager")`**；`return` 动作单独 `requireRole("owner")`。
2. `rbac.ts` 的 `requireRole` 需先修：DB 写入失败时的降级行为要明确（建议登录时 `admin_sessions` 插入失败直接 500，不要"登进去了但没权限"）。

## 五、退卡的写入模型

### 5.1 一次退卡写什么（单事务，一条 CTE）

| 目标 | 内容 |
|---|---|
| `member_cards` | `status='returned'`、`returned_at=NOW()`、`return_reason`、`updated_at=NOW()`；**`remaining_count` 不动** |
| `card_transactions` | 新增 `type='return_freeze'`、`amount=0`、`balance_after=remaining_count`、`note='退卡冻结'`、`created_by`、`idempotency_key` |
| `audit_logs` | `action='member_card.return'`、`entity_type='member_card'`、`entity_id`、`actor_type='admin'`、`actor_id`、`actor_role`、`reason`、`before_json`（退卡前完整卡快照）、`after_json`（退卡后完整卡快照）、`idempotency_key` |
| 幂等 | `card_transactions.idempotency_key` 唯一；`audit_logs.idempotency_key` 唯一；重复请求返回原结果 200 |

**期限卡（`category='period'`）口径**（2026-10-22 确认）：
- `remaining_count` 保持 `NULL`，**不写 0、不写任何虚构数字**
- 保留原始 `valid_until`、`valid_from`、`returned_at`、`card_type_id`、`price_cents`
- 会员端展示"有效期至 X（已退卡）"，不显示"剩余 0 次"
- 流水仍写一条 `return_freeze`，`amount=0`，`balance_after=NULL`

退卡**不写**：`members.freeze_status`、`attendance`、`trainings`、`photos`、`photo_comparisons`、任何计量/金额字段。

### 5.2 明确不做（对应规则 1.1-4 / 1.2-3）

- 不清零 `remaining_count`、不删卡、不删流水、不删照片
- 不写退款金额、不写"已退款"、不写支付成功状态
- 不自动取消会员未来的预约（见 6.3 待确认）
- 不自动恢复、不自动续卡

### 5.4 已退卡能否恢复（**2026-10-22 已确认：不提供恢复**）

**规则**：退卡不提供直接恢复。需要继续消费时，由店主按**新开卡流程**处理。

**实现口径**：
- 不提供 `restore` 接口，`returned` 是终态
- 后台打开发卡表单，给该会员**新建一条 `member_cards`**（新的 `id`、新的 `valid_from`、新流水）
- 旧卡状态、旧流水、旧审计**一律保持只读**，不因新卡而改变
- 会员端"我的卡"会同时出现"已退卡（历史）"与新卡，历史卡不参与任何可用性判断

**禁止**：
- 把旧卡 `returned` 改回 `active`（会让历史权益与新业务混在同一张卡上）
- 复用旧卡 `id` 续期
- 删除旧卡以"腾出"位置

### 6.3 未消课预约怎么处理（**2026-10-22 已确认**）

**规则**：退卡后不允许继续核销或使用权益；未来预约**保留历史记录**，由**店主处理**取消或特殊安排。

**实现口径**：
- 退卡接口**不自动取消**任何 `booked` 预约，不改预约状态、不删记录
- 该会员的预约记录照常可查（后台名单、会员端"我的预约"都能看到历史）
- 到了上课时间，教练端签到会被拒（无可用卡），由**店主线下决定**：取消、按个案核销、或另作安排
- 店主在后台手工取消该预约时：释放名额、不扣次、写审计（沿用 `POST /api/admin/reservations` 的后台取消）
- 会员本人仍可自行取消（`POST /api/portal/bookings/cancel`），释放名额、不扣次

**这是"系统不替店主做业务决定"的落地**：系统只保证"不能核销"，至于取消还是特殊安排，交给店主。

### 6.4 "只读状态"怎么落地

不引入全局中间件（风险高、影响登录），改为**写接口逐点校验**：所有会员端写接口在参数校验后加一句 `if (await isReturned(memberId)) return 403`。清单见 8.2。
